# Logging

## Architecture

Error handling and observability are deliberately separate concerns:

- **Errors still propagate.** Every unexpected failure (network, 5xx, unexpected 4xx) is left to bubble to
  the host app's own exception handler, per `plan §8` (`docs/2026-08-12-...-initial-plan.md`). The package
  does not wrap service calls in try/catch to log them — that would duplicate what the host's handler
  already does and risks inconsistent redaction across call sites.
- **The package owns two kinds of intentional, structured logging instead:** an audit trail of write
  actions (done), and — not yet built — Guzzle HTTP request/response tracing.

## Logger resolution — bind by instance, not just by config key

- `Sandstorm\FilamentKeycloakAdmin\Logging\KeycloakAdminLogger` — a marker interface (`extends
  Psr\Log\LoggerInterface`) used only as a container binding key. The host's bound instance does not need
  to implement it — any real PSR-3 logger (Monolog, `Log::channel(...)`, etc.) already satisfies
  `Psr\Log\LoggerInterface`, which is all the package type-hints against. `Psr\Log\LoggerInterface` itself
  is deliberately *not* used as the key, to avoid colliding with unrelated bindings in the host app.
- `KeycloakAdminLoggerFactory::resolve($app)` — checks `$app->bound(KeycloakAdminLogger::class)` at the
  point of use; if bound, returns that instance. Otherwise falls back to
  `Log::channel(config('filament-keycloak-admin.logging.channel'))` (`null` → app's default channel).
- The package never registers a binding for `KeycloakAdminLogger` itself (same pattern as
  `AdminKeycloakSession` — see `FilamentKeycloakAdminServiceProvider::resolveAdminKeycloakSession`), so
  there's no registration-order race with the host's own provider.

Host apps opt in with one line, no adapter class required:

```php
$this->app->singleton(KeycloakAdminLogger::class, fn () => app(\Psr\Log\LoggerInterface::class));
```

## Audit logging — write actions

`Sandstorm\FilamentKeycloakAdmin\Logging\LogsKeycloakAdminWrites` is the shared trait. It exposes exactly
two methods — the level/message pairing is fixed per outcome so call sites can't drift onto inconsistent
levels:

- `logKeycloakWrite(string $action, array $context = [])` — logs at **info**, message "Keycloak admin
  write succeeded".
- `logKeycloakWriteDenied(string $action, array $context = [])` — logs at **warning**, message "Keycloak
  admin write denied".

Both always log via a static PSR-3 message + context array — never string-interpolated. `admin_id`
(`Filament::auth()->id()`) is added automatically; callers pass only the `action` name and non-PII
identifiers (ids, flags, counts) in `context` — never request bodies, names, emails, or attribute values.

`InteractsWithKeycloakWrites::runKeycloakWrite(string $action, array $context, callable $write): bool`
uses both: info on success, warning on a 401/403 denial. That denial branch is the one place this package
swallows a failure into a UI notice instead of letting it propagate (plan §8's scoped exception,
`plan §7.2`) — without this log line it left no trace anywhere.

Current call sites, one `action` per write:

| Component | Action | Path |
|---|---|---|
| `KeycloakUserIdentity` | `user.set_enabled` | via `runKeycloakWrite` (info/warning) |
| `KeycloakUserIdentity` | `user.update_identity` | via `runKeycloakWrite` (info/warning) |
| `KeycloakUserGroupsTable` | `group.add` | direct `logKeycloakWrite` (success only — plan §8 applies unmodified) |
| `KeycloakUserGroupsTable` | `group.remove` | direct `logKeycloakWrite` |
| `KeycloakUserCredentialsTable` | `credential.send_password_reset_email` | direct `logKeycloakWrite` |
| `KeycloakUserCredentialsTable` | `credential.remove` | direct `logKeycloakWrite` |
| `KeycloakUserSessionsTable` | `session.logout_all` | direct `logKeycloakWrite` |

The five direct-call-site actions don't go through `runKeycloakWrite` (they never catch 401/403), so an
unexpected failure there still propagates unlogged-by-us, same as before this work.

## Config

`config/filament-keycloak-admin.php` → `logging.channel` (default `null`, meaning the app's default log
channel). Only consulted when the host hasn't bound `KeycloakAdminLogger` by instance.

## Open items

1. **Guzzle HTTP inbound/outbound tracing** — not yet built. Add middleware to the client in
   `FilamentKeycloakAdminServiceProvider::buildHttpClient()`: method, path, status code, duration only —
   never headers (`Authorization` bearer / client secret) or bodies (admin responses are full user objects
   = PII). Gate behind a new config toggle (e.g. `logging.http`, default `false`). The existing
   "non-body-logging" invariant in that method's docblock stays a hard rule, not a verbosity flag.
2. **phpstan/larastan** — `composer analyse` cannot run in this sandbox: phpstan's parallel workers need a
   local TCP listener (`tcp://127.0.0.1:0`), which the sandbox denies. Run it manually outside the
   sandbox, or decide whether to pin `parallel.maxProcesses: 1` in `phpstan.neon.dist` permanently.
3. **CHANGELOG.md** — not yet updated with the new `KeycloakAdminLogger` binding point and `logging.channel`
   config key.
