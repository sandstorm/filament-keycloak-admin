# Logging

## Logger

- `Sandstorm\FilamentKeycloakAdmin\Logging\KeycloakAdminLogger` — container binding key for a host-provided
  PSR-3 logger instance. Not bound by the package itself. Resolved via
  `KeycloakAdminLoggerFactory::resolve($app): ?LoggerInterface` — returns `null` when unbound, meaning no
  audit logging happens at all (no config-channel fallback).

## Audit logging (write actions)

- `Sandstorm\FilamentKeycloakAdmin\Logging\LogsKeycloakAdminWrites` trait:
  - `logKeycloakWrite(array $context)` — info, "Keycloak admin write succeeded".
  - `logKeycloakWriteDenied(array $context)` — warning, "Keycloak admin write denied".
  - Adds `admin_id` (`Filament::auth()->id()`) automatically. Callers supply
    `self::LOG_CONTEXT_ACTION` plus any other non-PII context (ids, flags, counts — never bodies, names,
    emails, attribute values).
  - No-ops (`$logger?->log(...)`) when no `KeycloakAdminLogger` is bound — nothing is logged, not even to
    a default channel.
- `InteractsWithKeycloakWrites::runKeycloakWrite(string $action, array $context, callable $write): bool`
  uses both methods (identity writes: enable/disable, edit identity) and is also where a 401/403 denial is
  caught and turned into a UI notice instead of propagating.
- Five other write actions log directly via the trait (no denial handling — failures propagate as before):
  group add/remove, send password-reset email, remove credential, logout-all-sessions.

## HTTP tracing

- `Sandstorm\FilamentKeycloakAdmin\Http\KeycloakAdminHttpHandlerStackCustomizer` — interface with one
  method, `customizeHandlerStack(HandlerStack): HandlerStack`. Host app binds an implementation
  (`$this->app->bind(KeycloakAdminHttpHandlerStackCustomizer::class, MyCustomizer::class)`) to add its own
  middleware; `FilamentKeycloakAdminServiceProvider::buildHttpClient()` resolves it, if bound, and passes
  the client's handler stack through it before building the client. The package adds no middleware of its
  own — token requests carry the client secret, admin responses carry user PII.

## Tests

- `tests/Feature/Logging/LogsKeycloakAdminWritesTest.php` — exercises `LogsKeycloakAdminWrites` through a
  bare host fixture (`tests/Fixtures/LogsKeycloakAdminWritesHost.php`) with an `InMemoryLogger`
  (`tests/Support/InMemoryLogger.php`) bound as `KeycloakAdminLogger`: success/denied levels+messages,
  `admin_id` from the current panel's guard, and the no-op case with nothing bound.
- `tests/Feature/Http/KeycloakAdminHttpHandlerStackCustomizerTest.php` — a
  `RecordingHandlerStackCustomizer` fixture proves the real `HandlerStack` is handed to the customizer
  exactly once and that middleware pushed onto it actually runs requests through the stack. Bound via
  `tests/Fixtures/BindsRecordingHandlerStackCustomizerProvider.php`, listed ahead of the package provider
  in `getPackageProviders()` — `getEnvironmentSetUp()` runs too late, since `buildHttpClient()` executes
  synchronously during provider registration.
- `tests/Feature/Http/KeycloakAdminHttpHandlerStackCustomizerAbsentTest.php` — the client still builds and
  resolves with no customizer bound.
- `tests/Feature/Logging/WriteActionAuditLogTest.php` — one audit-log assertion per real write action
  (identity enable/disable, identity edit, group add/remove, password-reset email, credential remove,
  logout-all), driven through the actual Livewire/Filament action lifecycle like the E2E suite but against
  in-memory `tests/Fixtures/FakeKeycloak*Api.php` fakes instead of a live Keycloak. Also covers both
  identity actions' denial (warning-level) path. The other five actions aren't tested for the
  exception-propagates-unlogged case — that follows directly from the code (the log call is unreachable
  after a throw) and didn't seem worth a dedicated test.
